# BusinessTarget Management V1

Status: Accepted for Work Item [#602](https://github.com/WebEnvoy/WebEnvoy/issues/602); owner: Core for local metadata, Grant, Run and results; Harbor for durable Account binding and Profile identity ownership facts. This specification complements [canonical product architecture §3.3, §5.4 and §12.3](https://github.com/WebEnvoy/.github/blob/main/docs/product-architecture-v1.md); it does not replace Account or BusinessTarget product semantics.

## Result and ownership

An installed Agent with an explicit current `agent_operations_v2` Grant may create, list, read, relabel and disable Core-local BusinessTarget metadata for the exact Accounts selected when that Grant was issued. The five operations are `business_target.create`, `business_target.list`, `business_target.read`, `business_target.metadata.update` and `business_target.disable`, exposed through the existing `webenvoy_operation` and queried through the existing Run query path.

Harbor remains authoritative for Account binding and its `identity_ownership.history.bindings` projection. Core issues a target-capable Grant only after a trusted owner selects one or more exact `(profile_ref, account_system_ref, account_ref)` tuples that Harbor currently reports as unique and runnable. Core stores those resolved tuples on the new Grant. Agent-supplied target requests cannot add or change these snapshots. A legacy Grant, a v2 Grant without the new field, or a Profile-only permission has no BusinessTarget access; readers never backfill it. Each operation rechecks the current Grant, exact Profile and task scope, the Grant's tuple snapshot, and Harbor's current matching unique/runnable binding.

The durable metadata key is `(account_system_ref, account_ref)`. `created_by_profile_ref` records provenance only and is not the metadata owner. A newly authorized Profile bound to the same stable Account tuple can read or manage the existing metadata; a different Account cannot enumerate its refs, labels, count or history. Harbor's aggregate Profile ownership status can be `conflict` while one other selected Account tuple remains unique; Core must make this decision per binding. Unknown, conflict, removed, ambiguous or archived/non-runnable binding rejects only the BusinessTarget operation that depends on it.

## Record and operations

The owner selection item is [`business-target-account-scope-selection.schema.json`](../../packages/schemas/schemas/business-target-account-scope-selection.schema.json); the persisted snapshot is [`business-target-account-scope.schema.json`](../../packages/schemas/schemas/business-target-account-scope.schema.json). The record contract is [`business-target.schema.json`](../../packages/schemas/schemas/business-target.schema.json); operation payloads are [`business-target-operation-result.schema.json`](../../packages/schemas/schemas/business-target-operation-result.schema.json). Core generates an opaque `business_target_ref`. The record contains the stable Account refs, a normalized label, an optional declared external ID, `status`, `verification_state: "unverified"`, the creating Profile provenance, timestamps, and a disable timestamp. Neither the reference nor `declared_external_id` identifies a verified external business resource.

`business_target.create` and `business_target.list` require the selected exact Account tuple. Creation accepts a label of 1–256 characters and an optional declared external ID of 1–256 characters; Core trims both and rejects an empty normalized value. It always returns `unverified` metadata and does not accept Agent-supplied refs, verification, ownership or provenance. List returns only records for that Account and has no cross-Account counts or pagination metadata.

`business_target.read`, `business_target.metadata.update` and `business_target.disable` take the opaque target ref and resolve the record's Account against the current Grant snapshot and Harbor binding. Update changes only the label. Disable preserves the ref, Account, declaration and history; disabled records remain readable, cannot be relabeled, and repeated disable is idempotent. No operation creates, edits, publishes or deletes a resource on an external site.

Malformed/unknown operation fields fail input validation; unauthorized operation, Profile or task scope fails `managed_access_denied`. A current conflict, unknown, non-runnable or changed binding returns `business_target_account_binding_conflict`, `business_target_account_binding_unknown`, `business_target_account_not_runnable` or `business_target_account_binding_changed`, respectively. A target ref that does not resolve inside the caller's authorized Account returns `business_target_unavailable` without disclosing another Account's record. Relabeling a disabled record returns `business_target_disabled`; changing a previously used idempotency key returns an idempotency conflict. A local receipt absent after an interrupted write is queried as `business_target_operation_not_applied`; query never reruns the operation.

Metadata grants no browser, Network, account-binding or business-write authority. There is no global catalog prerequisite for publishing. Existing site-specific prechecks and verifiers retain their own scope; a local declaration cannot substitute for fresh Harbor evidence that an external target exists or belongs to the selected Account.

## Runs, persistence and compatibility

Every operation uses the existing Core Run, result envelope, idempotency and `webenvoy_query`. Same key and same wire input returns the original Run/result; a changed input conflicts. After a lost response, query the original key or Run and do not replay with a new key. Local records and their receipts persist across Runtime restart and are written atomically under Core's local owner lock. If the atomic receipt exists, query projects its saved result; an already `unknown_outcome` Run remains unknown and retains its original failure history. If no receipt exists, query reports `business_target_operation_not_applied` without rerunning the operation. Unknown outcomes do not trigger a second external action because these operations make no external browser dispatch.

Grant account tuples are additive v2 persisted data. They are created only during issuance of a new Grant containing one or more BusinessTarget operations, by Harbor-backed owner resolution; they are never inferred from a pre-existing Profile or old Grant. Existing Grant revoke, expiry, Profile policy and task-scope intersections keep their existing semantics. Disabled metadata is retained; this Work Item defines no hard-delete path or Account binding mutation.

## Design obligation and limits

For #602, `DO-PLUGIN-EXPOSURE` and `DO-GRANT-WIRE` are `triggered` and are completed by the #602 sections in [Plugin Runtime Exposure V1](plugin-runtime-exposure-v1.md), [Grant Wire Contract V1](grant-wire-contract-v1.md), and the schemas/fixtures indexed in [Contracts](../contracts/README.md). `DO-NETWORK-CONTRACT`, `DO-CONSOLE-CONTRACT` and `DO-PROVIDER-PRIVATE-SCHEMA` are `not-triggered`: no Network, Console or Provider-private wire is added. `DO-APP-IA` is `not-triggered`: the frozen Desktop App is unchanged.

Real installed third-party Agent and live Account evidence remain separate Work Item acceptance evidence; this specification and fixture tests do not claim those checks passed. AccountSystem/Account binding ownership, automatic account binding, external business resource CRUD, bulk operations, permanent erasure, generic site verification and a global publication gate are outside this contract.
