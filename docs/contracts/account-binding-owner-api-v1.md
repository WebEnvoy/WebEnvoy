# Core Owner Account Binding API V1

Owner: WebEnvoy Core for the trusted-user route; Harbor for observation verification and persisted binding. Request schema: [`account-binding-owner-operation-request.schema.json`](../../packages/schemas/schemas/account-binding-owner-operation-request.schema.json).

The only route is `POST /owner/account-bindings/operations`, protected by the existing Core owner Bearer gate. Agent credentials cannot call it. Bodies are limited to 64 KiB and reject unknown fields. `inspect` returns the existing Harbor account-binding projection for one identity environment. `bind` requires `confirm: true`, the exact identity environment, Profile, Runtime Session, observation, AccountSystem, account refs, and an idempotency key.

Core reads the named owner Runtime Session through its internal Harbor supervisor route, verifies that its Profile and identity environment match the request and that its Core ControlLease is held, then derives `holder_ref` from Harbor's current session facts. The caller cannot supply a holder. Core sends the existing observation and derived holder to Harbor's account-binding route. Harbor remains authoritative: it checks the saved verified observation, performs a fresh observation, compares account system/ref and control generation, then persists through the existing identity-environment manager. This owner route does not add an identity observer, infer login state, or create another binding state machine.

Account refs are stable `account:sha256:<lowercase-hex>` references produced by Harbor's site observer. The owner selects and confirms an exact observed ref; the route does not accept a login name or raw identity evidence. Local AccountSystem definitions remain Core metadata and do not authorize or assert the observed identity. A Harbor-specific observer is separately owned by Harbor; neither a template nor Agent input can declare one.

The existing Core `profile.read`/`profile.list` Agent projection may expose Harbor's bounded `identity_ownership` summary, defined by [`profile-identity-ownership.schema.json`](../../packages/schemas/schemas/profile-identity-ownership.schema.json). Its current result comes only from one fresh trusted observation that still matches the live Session control generation and Page/document binding. Persisted bindings remain historical `verified_at_binding` evidence; the legacy `site.account_ref` remains a separate declaration. That declaration is projected only when both its stored account ref and derived `account-system:${site_id}` ref fit the schema's 1–256 character ASCII ref grammar; older values outside that bound remain unchanged in Harbor and its ownership checks but are omitted from the bounded summary. They are not normalized or promoted to verified identity. `ownership` is a Profile-wide summary: `unknown` without a durable binding, otherwise Harbor reuses its existing managed-binding conflict predicate and returns only `unique` or `conflict`, or `not_runnable` for an archived identity environment. Each persisted binding may also have its own `ownership_status` (`unique`, `conflict`, `unknown` or `not_runnable`) for consumers that authorize an exact tuple. Core preserves older projections without this field; it maps only aggregate `unique` to per-binding `unique`, aggregate `not_runnable` to `not_runnable`, and other missing per-binding conclusions to `unknown`. The projection never exposes colliding Profile refs, names or counts, does not add Agent write authority, and does not block otherwise authorized public Profile reads when a conflict exists. `account.bind` remains the only binding write and remains owner-only.

The GitHub observer candidate lives in Harbor's consumed shared-driver `observe_identity` path. On `https://github.com/<login>` it accepts a stable ID only when the page is ready, the path is exactly that profile, each of four single meta elements is present, the viewer `user-login`, profile `profile:username`, and `octolytics-dimension-user_login` values are valid and equal ignoring case, and `octolytics-dimension-user_id` is a positive decimal ID. The observer reads the current page only; it does not call `api.github.com` or issue a cross-origin request. GitHub's REST reference describes user `id` as durable while `login` can change ([Get a user using their ID](https://docs.github.com/en/rest/users/users#get-a-user-using-their-id)); the HTML meta names themselves are not a documented identity contract. A public profile with an empty viewer marker therefore remains unknown. The candidate requires a fresh dedicated authenticated-Profile observation proving that all four markers occur together and agree before GitHub account binding can be treated as supported. Any missing, duplicate, malformed, or mismatching signal stays unknown. This evidence gate does not let Core metadata or Agent input infer identity.

`account.bind` remains `not_exposed` to Agent capability projection. The owner CLI is the trusted-user entry. If a bind response is lost, the CLI reports `unknown_outcome` with the original idempotency key and does not retry. The owner can inspect current bindings with the same route before deciding what to do next; the route continues to use Harbor's existing idempotency receipt and fresh-observation gate.
