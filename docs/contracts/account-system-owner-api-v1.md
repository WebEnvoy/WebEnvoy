# Core Owner AccountSystem API V1

Status: Accepted for #475 and the #476 AccountSystem refresh slice. Owner: WebEnvoy Core. Wire schema: [`account-system-owner-operation-request.schema.json`](../../packages/schemas/schemas/account-system-owner-operation-request.schema.json). The API changes only Core-local public AccountSystem definitions; it does not discover accounts, bind an Account to a Profile, infer login state, or perform account reads or writes.

The sole route is `POST /owner/account-systems/operations`. It uses the existing Core supervisor Bearer credential and the shared owner gate. Agent credentials cannot access the route. Bodies are limited to 64 KiB and reject unknown fields. Every operation returns `{ "ok": true, "result": ... }`; errors return `{ "ok": false, "error": { "code": ... } }` without local paths or sensitive material.

Operations are `import_template`, `list`, `create_draft`, `create_refresh_draft`, `update_draft`, `check_draft`, `pin_draft`, `enable`, `disable`, `rollback`, and `resolve`. Import and refresh name immutable approved Lode template refs. `create_refresh_draft` also names the current local base revision; Core verifies the old and new source pins and the stable AccountSystem ID, then returns a three-way merge over public metadata. Unchanged local fields take the new template value; local-only edits remain; concurrent different edits to the same field are returned with their base, local, and template values and default to the local value.

`update_draft` may include `conflict_resolutions`, an array of JSON Pointer paths paired with `local` or `template`. Paths are limited to the mergeable public metadata fields in the request schema. Every reported conflict must receive an explicit choice before `check_draft` is valid; `pin_draft` rejects unresolved conflicts. Array-valued fields are treated as one merge field. Draft pin, enable, disable, and rollback require the current record version. Pinning creates an immutable revision carrying the new provenance but does not change the active revision. The owner explicitly enables the exact pinned revision with a second CAS. Rollback re-enables an exact historical revision and restores its provenance. `resolve` can inspect an exact historical revision only with `historical: true`; normal resolution refuses a disabled or non-current revision. Core validates the selected template index and exact template bytes before import, refresh, and draft check, and validates every edited definition against the selected pinned public template shape.

The API never accepts an Agent-provided template file, local path, credential, cookie, selector, executable code, Profile ref, or asserted authenticated state. A template import creates an enabled local metadata definition but is not a browser authorization or an Account/Profile binding. Refresh changes only the Core-local public definition; it does not mutate Harbor identity bindings or browser state. An AccountSystem-dependent task must independently resolve the enabled local revision before Run creation; tasks that do not declare an AccountSystem reference never consult this store.
